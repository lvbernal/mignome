# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

mignome — "Gnome como a mí me gusta". Bash and Python scripts that replicate the user's GNOME desktop setup on other machines. The config was captured on Ubuntu 26.04 / GNOME 50 (Wayland) and is meant to be iterated as the OS gets upgraded. User-facing text (README, script messages, comments) is in Spanish.

## Commands

- `./install.sh [step...]`: apply the config. Steps: `packages fonts cursor sounds extensions dconf theme` (default: all). Run as the user inside a GNOME session, not as root.
- `./theme.sh [name]`: list themes, or apply `themes/<name>/`. The active theme is stored in `~/.local/state/mignome/theme`.
- `./export.sh`: regenerate `dconf/*.ini` from the current machine's dconf database.
- `./check.sh`: validate every key in `dconf/*.ini` against the installed GSettings schemas, extension schemas included. Exits 1 on problems.

There are no tests. To verify a dconf load without touching the live config, load into a throwaway database: `DCONF_PROFILE=<file containing "user-db:mignometest">` → `dconf load /` → `dconf dump /`, then delete `~/.config/dconf/mignometest`.

## Architecture

- `install.sh` runs `steps/NN-<name>.sh` in order. Each step is standalone, sources `lib/common.sh`, and is idempotent.
- `config/` holds plain lists that the steps read with `read_list` (`#` comments allowed): apt/snap packages, and `extensions.txt` (`ego|system  uuid  enabled|disabled`). The extensions step writes `enabled-extensions` and `disabled-extensions` **exactly** from that list, so running it on the reference machine disables anything not listed.
- `dconf/*.ini` is **generated** by `tools/mignome.py export` from a whitelist (`RULES`: output file → dconf section paths, with `/*` meaning a subtree, plus per-rule and global key exclusions). Change what gets captured by editing `RULES`, not by hand-editing the `.ini` files, or the next export overwrites the edits. `$HOME` is stored as `@HOME@` and substituted at load time.
- Extension enablement is deliberately kept out of `dconf/shell.ini`; it lives in `config/extensions.txt`.
- Themes (`themes/<name>/`) own the keys in `THEME_KEYS` (accent-color, color-scheme, gtk-theme, icon-theme) and the Ptyxis profile `palette`. Export excludes them, so `dconf/` never depends on which theme is active. `default` must keep matching the original setup. A theme can also ship `gtk-4.0.css`, which `theme.sh` writes to `~/.config/gtk-4.0/gtk.css` with a `/* mignome-theme:` marker on the first line. Without that marker, the existing file is treated as the user's own and backed up, never overwritten.
- Editor theming (`tools/vscode.py`): `EDITORS` maps each CLI to its `~/.config/<dir>/User/settings.json` (`code` → `Code`, `kiro` → `Kiro`). Add another VS Code fork by adding a line there. `themes/<name>/vscode/` is a normal theme extension, shared by all editors. The anniq-light extension ships both "Anniq" and "Anniq Dark", and `themes/anniq-dark/vscode` is a symlink to it. `apply <editor> <dir> [label]` zips it into a VSIX (no `vsce` or npm needed), installs it with `<cli> --install-extension --force`, and sets `workbench.colorTheme` to the label from the theme's `vscode-theme` file (or the first declared label). Bump the extension `version` whenever a theme JSON changes. `settings.json` is JSONC, so it's edited as text: a scanner masks strings and comments, only the `workbench.colorTheme` entry is replaced, inserted, or removed, and the result is re-parsed before an atomic write. The previous value (or `__unset__`) is saved per editor in `~/.local/state/mignome/<cli>-previous-theme`, and `restore-theme <editor>` puts it back. To test without touching the real editors, point `XDG_CONFIG_HOME` and `XDG_STATE_HOME` at temp dirs, and put `code`/`kiro` wrappers first in `PATH` that add `--extensions-dir`/`--user-data-dir` pointing at temp dirs. Kiro 1.4 is based on VS Code 1.131, which supports every color key the theme uses. Unknown color keys are silently ignored by VS Code, so check new keys against `workbench.desktop.main.js` or the built-in extensions' `package.json` (the `gitDecoration.*` keys come from the git extension).
- Shell theming (`tools/shelltheme.py`): the shell loads the User Themes stylesheet as `application_stylesheet` on top of the session's `default_stylesheet`, which is Yaru for `--mode=ubuntu` and already picks its `-dark` variant from `color-scheme` (see `_getDefaultStylesheet` in the shell's `ui/main.js`). So a theme only needs overrides. The generator extracts the base CSS from the mode's `themeResourceName` gresource, regex-replaces color tokens per `themes/<name>/gnome-shell.json`, and emits only the changed declarations, keeping `!important`. The tokens are `-st-accent-color`/`-st-accent-fg-color`, hex, rgb/rgba matched by RGB, `white`, and `black`, with near-neutral greys tinted. Selectors are kept verbatim. St has no CSS variables, which is why accents are replaced per rule. The CSS is generated at apply time into `~/.local/share/themes/<name>/gnome-shell/`, so it follows Yaru upgrades. `theme.sh` sets `user-theme name` to `''` first to force a reload. System indicator colors (recording, screen sharing, battery warning) are intentionally left unmapped. The User Themes stylesheet outranks extension stylesheets, which in turn outrank Yaru. So re-emitting a Yaru rule that an extension overrides makes Yaru win again, even with the theme's colors. The map's `skip` regexes drop such selectors. For example, `#dash .dash-item-container …` and `#dash .dash-background` are skipped so that Ubuntu Dock keeps its transparent icon tiles. When something an extension styles looks wrong under a theme, compare the extension's `stylesheet.css` with the generated CSS and add a `skip` pattern. Since `user-theme` is a theme-owned key, export excludes its section.
- `anniq-dark` is derived, not taken from the web app: the Vuetify palette only defines light mode. Dark surfaces come from `menu-bg` (#0B2211), text is the light theme's background (#F1F8F6), and the accent is `secondary` (#C7FC8B) with #1B2528 text. Don't use `brand` (#9BFF2E): the user finds it too harsh, so `secondary` replaces it everywhere, with `secondary-soft` (#E5FDCF) as the lighter variant. It reuses anniq-light's `Anniq.palette` (the `[Dark]` section) and VS Code extension through symlinks, so changes there affect both themes.
- `everforest-dark`/`everforest-light` use sainnhe's Everforest medium palette (MIT). Ptyxis ships a built-in `Everforest` palette, so neither theme has a `.palette` file. `everforest-light/vscode` is a symlink to `everforest-dark/vscode`, which ships both labels. Everforest light colors are below 4.5:1 as text on `bg0`, so wherever a color is used as text (accent, links, states) it's mixed with `#2D353B` until it passes, e.g. green `#8DA101` → `#677618`. Backgrounds keep the original color with `#2D353B` text. VS Code token colors follow the Vim scheme: keywords red, functions green, strings aqua, types yellow, properties blue, numbers purple.
- `eyes-dark` is mignome's own palette, aimed at reducing eye strain. Colors were built in OKLCH: backgrounds at hue 70 with chroma 0.009 (`bg_dim` #1A1713 L0.205, `bg0` #211D1A L0.235, `bg1` #282521, `bg2` #302C28, `bg3` #3A3632, `bg4` #44403C, in steps of 0.03 to 0.04), text #D9D0C1 at L0.86 (10.9:1, deliberately not pure white), and accents at L0.76 with chroma 0.055 to 0.09 (7 to 8:1 on `bg0`): amber #D3A974 (the accent), red #DE958E, orange #D8A485, yellow #C1B176, green #9EBC8F, aqua #89BEAF, blue #8EB8CE, purple #C5A4C6. Bright terminal variants are at L0.83. Keep new colors inside those lightness and chroma bands rather than adding saturated ones. Links are blue so they differ from the amber accent. The Ptyxis palette has no `[Light]`/`[Dark]` sections, so it applies in both modes. The VS Code JSON reuses Everforest's color keys. Syntax colors: keywords red, storage orange, functions blue, strings green, types yellow, properties aqua, numbers and constants purple, variables in plain text.
- `themes/anniq-light/gtk-4.0.css` overrides libadwaita 1.9 CSS variables, plus Ubuntu's `--yaru-accent-*` and `--yaru-link-*`. Surface variables sit inside `@media (prefers-color-scheme: light)`, so apps that force dark mode stay readable. To check a CSS change without touching the desktop, point `XDG_CONFIG_HOME` at a temp dir containing `gtk-4.0/gtk.css`, build an Adw window in Python without showing it, and read `widget.get_color()` under `Adw.ColorScheme.FORCE_LIGHT` and `FORCE_DARK`.
- `tools/mignome.py check` maps dconf paths to schemas via `gsettings list-schemas --print-paths`, run once for the system and once per extension `schemas/` dir. Several schemas can share a path (e.g. `org.gnome.mutter` and `org.gnome.mutter.devkit`). Relocatable schemas (Ptyxis profiles, custom keybindings) are matched by regex in `RELOCATABLE`.

## Constraints

- Never run `git commit` (or anything that creates commits, such as `git commit --amend` or `git merge`). The user makes all commits. Leave changes in the working tree.
- No applications: don't install apps (the only exception is the Bing Wall snap, for the wallpaper), and don't capture dock favorites (`favorite-apps`) or the app grid layout. Preferences of Ubuntu's default apps (Ptyxis, Nautilus, Text Editor) are fine. VS Code and Kiro are themed only if they're already installed, and never installed.
- Never capture secrets or personal data: network/VPN (`nm-applet`), bookmarks, histories, file-chooser paths, per-app notification lists, monitor layout.
- Shell pipelines run under `set -o pipefail`. Avoid `cmd | grep -q`: grep exits early and the SIGPIPE turns a match into a failure. Capture the output and test it instead (see `has_font` in `steps/20-fonts.sh`).
- The dock is Dash2Dock Animated (`dash2dock-lite@icedman.github.com`, for macOS-style magnification). It conflicts with Ubuntu Dock, so `ubuntu-dock@ubuntu.com` stays `disabled` in `config/extensions.txt`. Ubuntu Dock's `disable-overview-on-startup` no longer applies, so Just Perfection's `startup-status=0` keeps login on the desktop (1 opens the overview). That is Just Perfection's only job here. Keep its `theme=false`: its own styling turns the workspace-switch popup dots into rectangles and restyles Alt+Tab, the OSD and the shell font size. The old `dash-to-dock` section in `dconf/extensions.ini` is still exported but has no effect. Keep Dash2Dock's `icon-resolution=2`: the extension renders icons at a fixed base size (32 × the quality factor) and scales them, and the default (96 px) halves to ~48 px at rest with a bilinear filter, which looks pixelated. 64 px stays sharp at rest and only softens slightly at peak magnification.
- The cursor theme is installed in `~/.local/share/icons` and symlinked into `~/.icons`. The VS Code snap runs on XWayland with core20's libXcursor 1.2.0, which only searches `~/.icons:/usr/share/icons:/usr/share/pixmaps`. Without the link it silently falls back to the `default` theme (Adwaita).
- Vicinae and Open Bar were removed from the reference machine (Open Bar has no GNOME 50 version). Don't add either one back.
